# 低延迟音频与音画时钟优化实测

已将客户端 AAudio 阻塞写入改成原生回调与有界 PCM 队列，修正设备帧位置到实际媒体 PTS 的映射，保留音频时钟驱动的视频调度。最终 APK 已装入专用 Android TV 模拟器；会话结束后 core 确认 Idle、主机和客户端已停止，5004 / 5006 无串流监听。

## 相同逐帧方法的前后对照

Windows / RTX 4070 SUPER / Android TV API36 x86_64 模拟器 / c2.goldfish.h264.decoder。真实桌面 + 系统音频，1920×1080 / 60 fps / H.264 NVENC / TCP，音画同步与完整 trace 开启。每次进入 Playing 后采样 35 秒，报告排除前 5 秒；采样期间不运行编译或测试。使用同一 Rust 报告器与时钟探测口径，时间边界为捕获输出到 MediaCodec Surface 报告的呈现时间。

两组中位降幅分别为 **4.531ms、17.302ms**。旧版自身存在约 18ms 的会话间波动，优化后的中位约 125–130ms；这些短样本不能证明一个固定的降幅或稳定的性能排序。P99 帧间隔也没有全面改善，不能把降低缓冲说成已经解决全部卡顿。

对照 1 的音频实现与最终版一致；最终版额外记录同步成功 / 时钟缺失计数。首次旧版采样曾无法进入稳定播放，重启模拟器后重新取得有效基线；那条超时日志不参与数字对照。

最终版完整 trace：1785 个稳态呈现帧全部匹配主机；非法行、重复行、主机 / 客户端 trace 队列丢弃均为 0；跨时钟半 RTT 不确定度 P95 为 0.286ms。最终累计 2121 个解码输出全部按音频时钟请求呈现，时钟缺失回退 0、主动过晚丢弃 0。最后回调以前 2 秒的请求呈现输出中，仍有 21 个没有对应呈现记录；这不等于物理屏幕丢帧，但必须保留。

Surface 与音频目标差的最终 P95 为 +3.063ms，P99 为 +8.640ms；该指标验证请求调度与报告的呈现时间，不是用摄像机测到的音画物理偏差。系统音频在桌面样本中大多接近静音，也没有闪光 / 声脉冲同步标记，所以尚未完成真实可见、可听的音画同步验收。

## 最终音频行为与限制

- 原生实时回调仅做预分配 PCM 复制、补零与有界时间线发布，不调用 Java、网络、分配器、睡眠或阻塞写入。
- PCM 单生产者 / 单消费者队列：快速设备至少 20ms 上限，慢设备保留两轮回调。本模拟器为 1920 帧 / 40ms；设备缓冲也为 1920 帧 / 40ms。这些配置不能相加代替实际播放时间戳测量。
- 慢设备启动前预填两轮回调；快速设备保留 10ms 启动阈值。设备缓冲以两轮回调为目标，实际值由 API 查询。
- 回调记录设备帧、真实 PCM 累计帧和媒体 PTS；补零不推进已收到音频的播放证据。Java 使用一个完整不可变时钟快照，校验设备时间戳新鲜度和 RTP 回绕；设备位置不能再简单减零点后假定等于媒体位置。
- 断开错误由原生错误回调报告，网络 worker 重建设备；媒体时间跳变需要停稳输出并 flush 后重建映射。core 仍依据实际音画推进与资源释放作状态判断。
- 最终设备欠载计数 0、音频重置 0、时间线记录丢弃 0。回调 PCM 不足计数 9：最初反馈已记录启动补零 3840 帧 / 80ms；后来增加 128 帧 / 2.667ms，发生在反馈序号 70。不能宣称整个会话零断音。旧版未记录客户端 PCM 补零，无法直接比较该指标。

模拟器实际 AAudio mode 仍为 10 / NONE，**并未取得 LOW_LATENCY**；`dumpsys media.audio_flinger` 报告 No FastMixer，输出写延迟均值约 83ms。这是当前模拟器的限制证据，但不是单独测出的全部端到端延迟来源。缩小设备缓冲 50.8ms，不能期待整条链路必然降低 50.8ms。

## 被实测否定的更激进设置

将应用 PCM 队列压到一轮回调，35 秒内出现 250 次 PCM 不足、28480 帧补零，捕获到 Surface P50 升至 364.265ms。只压设备缓冲到一轮则出现 1492 次设备欠载、25 次重置，音频时间戳失效；其很低的视频中位值来自同步失效后的立即呈现，**不算优化收益**。这些设置均已撤回，最终保持两轮安全缓冲。
