# 桌面浮窗与焦点切换架构

游戏保持在虚拟屏幕上，用户通过浮窗或快捷键在游戏与之前的工作窗口之间切换焦点。这让用户临时使用电脑后快速回到电视游戏；同一登录会话仍只有一个前台窗口，并不保证游戏后台输入可用。

## 状态与适配器

```mermaid
flowchart LR
    UI[Windows 原生浮窗] -->|FocusCommand| FC[core FocusCore]
    FC -->|FocusEffect| WA[input Windows 焦点适配器]
    WA --> OS[Windows 窗口系统]
    OS -->|前台事件与窗口身份| FC
    FC -->|FocusSnapshot| UI
    UI -->|SpaceCommand| GC[core GameSpaceCore]
    GC -->|有序 SpaceEffect| AD[异步 Windows 屏幕与会话适配器]
    AD --> DRIVER[签名虚拟屏幕驱动]
    AD --> RUN[当前实验运行器]
    RUN --> MEDIA[原生捕获 编码 音频与同步]
    AD -->|实际资源与完成证据| GC
    GC -->|SpaceSnapshot| UI
    SC[已有 core Session Runtime] -.后续会话整合.-> MEDIA
    MEDIA --> TV[Fire TV]
```

`FocusCore` 是无系统调用的状态归约器，负责当前归属、工作窗口记忆、允许的命令、请求编号、确认和超时。`FocusSnapshot` 可由 TUI 和后续桌面界面复用。当前实验由桌面进程持有焦点和屏幕生命周期归约器，异步适配器与独立运行器执行媒体启停；原 Windows 主机的 Session Runtime 保留原功能，没有接管这轮独立媒体实验。焦点操作不重启媒体。

Windows 焦点适配器位于 `crates/input/src/focus_adapter.rs`，窗口身份包含句柄、进程编号和进程创建时间。执行切换前重新校验身份，避免把已经复用的窗口或进程当成原来的工作应用。适配器不注入游戏进程、不伪造后台焦点，也不会连续自动夺回焦点。

`apps/desktop` 创建原生浮窗并监听系统前台事件。界面只根据 core 提供的状态和命令更新，不自行判断切换成功。小范围周期检查用于窗口存活与请求超时；帧捕获、编码、音频时钟与网络均不经过浮窗。

正式主机整合时，通过本机 IPC 发布 FocusSnapshot、接收 FocusCommand，并将焦点会话绑定到媒体 session token。当前实验未将焦点命令开放到电视局域网协议，也未将桌面进程变成第二个媒体主机。

## 浮窗交互

浮窗置顶且显示时不激活，持续标注“游戏获得焦点”或“电脑正在使用”。这些标签描述实际焦点归属，不代替媒体健康或手柄连接状态。“返回游戏”选择绑定的游戏窗口；“拿回电脑”选择最近一次实际使用的工作窗口。浮窗自身和桌面外壳不会覆盖工作窗口记忆。

配置电视专用屏幕后，core 同时接收游戏窗口的位置证据。游戏改分辨率或自行回到主屏时，界面标注“游戏离开串流屏幕”；“移到电视屏幕”只移动并适配窗口大小，不抢工作焦点。“返回游戏”同时恢复位置和游戏焦点，两个条件均确认后才完成请求。位置修复仅由用户命令触发，避免与游戏不断争夺窗口位置。独占全屏或拒绝移动的游戏需要在游戏内选择显示器或切换窗口模式。

Ctrl+Alt+F9 拿回电脑，Ctrl+Alt+F10 返回游戏。快捷键注册冲突时界面明确提示使用按钮。游戏窗口退出后禁用游戏切换，工作窗口退出后禁用返回该窗口，保留手动选择其他工作窗口的路径。关闭浮窗本身不发送 Steam 游戏退出命令；实验运行器会正常停止测试串流并恢复窗口位置。

切换请求显示“正在切换焦点”，实际前台窗口确认后才显示成功。Windows 拒绝或确认超时，保留真实焦点归属并显示 Alt+Tab 的处理路径。[Windows 前台规则](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)

## 实验运行与回退

当前实验使用 Lost Judgment 和真实 Fire TV。运行器仅在原主机处于 Idle 时启动，要求唯一的非主屏 1080p 虚拟显示器。仍采用 High profile、P4 ULL、无限 GOP、一帧 VBV、四帧客户端队列、AAudio 低延迟输出和启用的音画同步。按游戏进程捕获音频，不改变默认设备；电脑端游戏声音静音仍是单独的后续工作。

构建 `cargo build -p sofalink-desktop`；独立浮窗入口为 `desktop.ps1`。完整实机实验入口为 `experiments/game-space/run-focus.ps1 -Device <Fire TV IP> -Python <GStreamer Python> -Seconds 600`，需要 PowerShell 7。关闭浮窗或到达实验时限后，运行器通过标准输入正常停止媒体，返回电视启动页并恢复游戏原窗口位置。虚拟显示驱动的申请与回收由 GameSpaceCore 排序，经异步适配器调用 `display-driver.ps1`，只回收拥有记录的设备。

当前可用版本的回退点是 `baseline-tv-2026-10-12`。实验配置、凭据、逐帧日志和本机窗口证据保存在忽略的 `local/game-space`，不进入公共仓库。

## 本轮实机验证

### 虚拟屏幕管理增量（2026-10-13）

默认 `desktop.ps1` 已改为管理界面，无须先启动游戏。`-FocusOnly` 保留旧入口。core 的 GameSpaceCore 驱动检查、创建、启动、串流、停止、恢复窗口、回收和卸载状态，GUI 只呈现快照与允许的命令。媒体工作仍走独立实验适配器，未合并到正式 Session Runtime；TUI 尚未接此管理入口，但可复用同一纯 Rust 契约。

开始先检查 Fire TV 调试授权，再经 Windows UAC 创建拥有记录的屏幕。适配器重新探测显示句柄，启动 Lost Judgment，并要求连续两次实际电视音视频进度及同步证据才确认串流。结束先等媒体运行器退出，再把同一进程身份的游戏窗口移回主屏；连续位置确认后才回收显示设备。窗口已经退出则归档原归属记录，不能移动复用该 PID 的新进程。

设置里的彻底卸载仅在媒体、窗口恢复与设备资源全部释放后可用。适配器验证签名和源 INF 的精确哈希，只删除对应 Windows 驱动包，不使用强制删除或重启标志。源安装包留在本机供下次开始重新安装。

启动期间取消会等待在途系统操作结果再清理。媒体启动前即保存运行器 PID、创建时间和停止标记，避免日志尚未发布时误判已停止。运行器校验管理进程创建时间，音视频进度停滞五秒后退出；界面在后台监控会话独立健康记录，失效后由 core 发出相同清理流程。此超时用于故障检测，没有改变媒体缓冲和同步参数。

界面正常关闭等待清理完成。被强杀或系统异常留下的设备／窗口记录，在下一次启动时提示恢复并阻止新会话。管理进程和异步操作分别有系统互斥锁，避免多个界面或旧授权操作交错。恢复失败时保留资源状态和重试入口，不能显示已回收。

本轮 Rust 全仓检查、生命周期契约和 PowerShell 语法检查通过；本机遗留失效窗口记录已通过实际恢复流程归档，当前无活动虚拟屏幕。Fire TV 重新授权由用户暂缓，创建／结束／彻底卸载的完整实机回归尚未完成。以下实机结果属于上一轮焦点浮窗验证。

用户确认浮窗操作正常。Windows 前台证据记录了返回游戏和拿回原工作窗口的请求与确认；游戏进程退出后，core 禁用了游戏命令，运行器停止媒体并返回电视启动页。窗口移动功能和位置确认已实现；用户反馈更新后的操作正常，分辨率重设导致窗口自行重建或独占全屏等情况仍需更多游戏回归。

Fire TV 使用 AAudio 模式 12，音频积压样本约 34 ms，音画同步保持开启。滚动帧率接近 60 fps，但存在低于 60 的采样窗口；本轮是交互验证，未用相同游戏片段做完整延迟前后对照，不能据此宣称物理端到端延迟没有变化。

后续将焦点契约接入主机本地 IPC 和 TUI。电视键鼠回传接入前，还需在电脑持有焦点时阻止游戏键鼠注入并释放已按下的输入；电视端不应因任意手柄操作自动抢走电脑焦点。本轮使用直接连接电脑的手柄，没有启用 TV 输入回传。
