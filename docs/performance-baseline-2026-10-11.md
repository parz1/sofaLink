# 2026-10-11 串流性能基线

结论：当前**主要延迟来自客户端音频积压及音画同步调度**；长帧主要发生于客户端解码输出/虚拟呈现路径。现在没有证据支持先换 Rust/C++ 或更换主机编码器。

Windows 桌面 1920×1080、目标 60fps、NVENC H.264 20Mbps、TCP 视频及 PCM 音频；客户端 Android TV API36 x86_64 AVD，Goldfish 解码器和 AAudio。PC 为 RTX4070 SUPER + Ryzen5700X3D。这是模拟器数据，不代表真实 Fire TV，也不是负载中的游戏性能或按键到屏幕测量。

## 可以确定的瓶颈与仍待验证的归因

1. **音频输出路径是延迟优先项。** 实际 AAudio mode=10（NONE），请求 LOW_LATENCY 未获得；burst=2180 帧（45.4ms）、buffer=capacity=4360 帧（90.8ms）。测得音频积压约 158–164ms。主机音频队列每秒 P95 的 P95 只有 0.142ms，发送阻塞对应值 0.189ms，不能解释百毫秒等待。证据指向客户端音频输出/缓冲及其时钟同步；尚未测量物理音频播放延迟，不能把全部积压等同于某一个内部缓冲。
2. **长帧主要发生于客户端路径，不能由旧的接收间隔归因。** 旧逐帧结局记录只包含获得呈现/丢弃结局的帧，因此接收间隔约 34ms 有选择偏差。修正为独立全帧接收后，一轮真实桌面采样得到主机 RTP 间隔 P95 18.06ms / 全部收到帧间隔 P95 20.39ms / Surface 间隔 P95 32.73ms。该轮累计收到 2133、提交 2114、解码输出 2114、请求呈现 2107、观察到呈现回调 1903；接收/提交/解码总吞吐接近，呈现反馈明显少于请求，当前线索集中在客户端输出/虚拟 Surface。解码输出等待 P95 30ms 包含调度与背压，不能直接当作纯硬件解码速度。现在是同机模拟器/ADB 转发，尚未测试 LAN 或真实 Fire TV，不能认定 Wi-Fi 丢包或 TCP 队头阻塞。修正采样见 [全帧接收报告](../local/diagnostics/all-arrivals/report.md)。
3. **呈现回调明显迟到，影响旧帧率口径。** 原来的延迟字段已经使用呈现时间，未把回调延迟加进去；旧帧率按回调计数的送达窗口计算，会把回调分批送达混入“是否流畅”。已改为按 Surface 时间间隔算 fps，并单独显示回调迟到；反馈过期和最新呈现超过 2 秒仍被检测。窗口内长帧是独立指标，平均 fps 正常也不证明流畅。

Surface 报告时间可能早于请求目标（同步轮 P50 早约 9.6ms），保留该差值；模拟器的调度兑现需要继续验证。等待回调的记录被淘汰也不能直接认定媒体被主动丢弃。

## 观察开销与补充证据

补上独立解码输出后，连续两轮得到以下结果。第二轮在进入 Playing 后用 MENU 隐藏统计层，原始反馈确认除启动时的 7 条反馈外，后续 132 条 `statsVisible=false`。这一对照没有恢复流畅度，不能把统计层绘制当成已经确认的主因。

| 完整接收/输出记录 | 统计层可见 | 统计层隐藏 |
|---|---:|---:|
| 全部接收间隔 P95 | 27.50ms | 24.32ms |
| 全部解码输出间隔 P95 | 38.79ms | 37.57ms |
| 全部解码输出等待 P95 | 75.06ms | 41.96ms |
| 呈现间隔 P95 | 32.75ms | 34.20ms |
| 观察到的稳态呈现 fps | 52.26 | 46.45 |
| 客户端排队 P95 | 151.65ms | 146.45ms |
| 采集输出到 Surface 估计 P50 | 280.86ms | 241.13ms |
| 早于最后回调 2 秒的请求呈现输出 / 无呈现记录 | 2074 / 240 | 1950 / 376 |

该轮把正常的末尾回调迟到排除后，仍有持续缺失；接收/解码总吞吐接近目标，解码输出节奏有明显批次/长间隔，Surface 呈现不足。具体线索是 **MediaCodec 输出调度/Surface 呈现及其背压**，需要系统追踪确认内部原因，不能等同于 NVENC 或纯硬件解码性能不足。客户端声音积压仍约 162ms，但请求同步等待可达约 203ms，下一步还要检查声音时钟映射/初始对齐，不只看 buffer size。

两轮环境存在波动，采样期间也有短暂代码检查，因此不能把隐藏统计层当作严格随机化性能实验。原始完整报告：[全部输出](../local/diagnostics/all-outputs/report.md)、[隐藏统计层](../local/diagnostics/outputs-hidden/report.md)。

同版本、同步开启的桌面场景，完整 trace 开/关各一轮 35 秒。取 8 秒后的 29 个秒级快照：

| 秒级窗口指标的中位数 | 完整 trace 开 | 完整 trace 关 |
|---|---:|---:|
| Surface 窗口 fps | 52.87 | 54.09 |
| 窗口呈现间隔 P95 | 32.88ms | 32.64ms |
| 窗口解码输出 P95 | 27.18ms | 27.25ms |

完整 trace 的增量开销不是当前波动的主要解释，但只有一对试验，不能声明零开销。这些是窗口分位数的中位数，不是全体帧的全局分位数；关闭 trace 时轻量窗口测量仍开启。

增加独立接收/输出记录后，再次用同一 APK 关闭 trace 采 35 秒，取 8 秒后的 30 条快照：窗口 fps 中位数 47.75、窗口呈现间隔 P95 的中位数 36.11ms、解码输出等待 P95 的中位数 89.98ms、排队 P95 的中位数 170.12ms。完整 trace 可见统计层轮的对应值为 51.81 / 32.78ms / 75.17ms / 71.98ms。**关闭 trace 未消除长帧和客户端积压**；会话间环境波动明显，这并不证明 trace 没有开销。不得把完整诊断时的某一轮耗时当成固定性能。

所有主要报告中主机 trace/客户端 trace/反馈任务队列丢弃为 0，非法行和重复记录为 0。UDP 诊断包无确认，启动/停止及未观察到呈现回调会造成总行数差异，不能把总行数差当成丢包率。

同步轮中额外取了一次 [Android gfxinfo](../local/diagnostics-gfxinfo.txt) 与 [CPU 快照](../local/diagnostics-android-top.txt)：应用 UI 帧 P95 38ms，有 Slow issue draw commands；Goldfish/Composer 也有明显运行负载。这只是环境线索，**gfxinfo 的 UI/统计层帧不等于视频 Surface 帧**，快照不能证明某线程为根因，查询本身也有开销。

## 下一步顺序

先独立验证客户端低延迟音频输出：实际能否获得快速路径、回调式输出与有界 PCM 缓冲、burst 与积压、初始时间映射/同步偏移、underrun/重置及音画偏差。以测量结果确定参数，不盲目压小缓冲，也不以关闭同步冒充优化。

再追客户端接收与呈现的长帧：保持相同视频负载，做调度追踪及真实 Fire TV 对照，把模拟器/ADB、解码输出、Surface 合成分别验证。主机 NVENC 和控制层语言暂时不是优先项。

实现与验证：新增 core 测量状态、Rust 离线分析、Java 时间窗口/时钟估计测试；统一 Rust 检查、7 个状态场景、Java 检查、APK 构建安装通过。多轮真实串流均完成开始、播放、结束和释放；最终测试图/测试音短采样也报告实际低延迟模式未获及音画同步等待。使用方法见 [性能诊断](performance-diagnostics.md)。
