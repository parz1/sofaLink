# 开发路线

## Milestone 1：从电视开始，到电视结束

首次设置完成后，用户坐在电视前，选择已配对电脑并点击“开始游戏”；电脑自动进入 Steam 大屏幕，电视开始串流。用户选择游戏并实际游玩，退出游戏回到大屏幕；选择“结束会话”后退出大屏幕、停止串流、恢复电脑声音与输入状态，电视回到本应用启动页。

Milestone 尚未完成。实现以 Windows 主机和当前 Fire TV 为首个实机验收组合，策略和状态契约保持通用。正式项目名为 sofaLink，GitHub 仓库名同名。

### 使用边界

- Windows 已开机、主机服务可用，Steam 已安装并登录；首次配对与授权可以需要设置步骤，日常操作不依赖电脑上的 TUI、终端或 ADB。
- 电视遥控器负责主机选择、开始、状态查看和结束；游戏主输入以手柄为目标，必须明确验证游戏内输入，不能把方向键映射当作原生手柄支持。
- “退出游戏”回到 Steam 大屏幕；“结束会话”退出大屏幕并返回电视启动页。默认保留 Steam 后台客户端，不关机，也不将其他已有程序算成本次会话资源。
- 退出应走正常退出路径，并确认实际状态；未完成的保存/退出界面和退出失败显示在状态中，不能只断开画面就报告结束成功。
- macOS、Jellyfin、媒体库、唤醒电脑、电视开机/HDMI 控制、桌面 GUI 与 Agent 暂不纳入此 milestone。

### 验收标准

1. 电视一键开始：连接已配对主机，确认 Steam 大屏幕就绪，取得真实音视频和输入反馈后显示“可游玩”；没有进程/播放证据时只显示正在启动或具体错误。
2. 实际游玩：至少一款明确记录的 Steam 游戏，从电视选择、启动并持续游玩至少 20 分钟；记录输入方式、游戏内输入、音画同步、颜色、帧间隔与同一套逐帧性能数据。目标串流 1080p60，不把桌面导航、模拟器数据或单次平均 FPS 当作游戏验收。
3. 两级退出：游戏内正常退出回到大屏幕；电视结束会话后确认大屏幕退出、串流资源释放、按键/手柄状态释放、电脑原静音状态恢复，电视显示可以再次开始。
4. 连续闭环：至少 5 次开始→游玩→结束，覆盖 Steam 已打开和未打开两种情况；没有遗留会话、卡住的输入或静音状态。
5. 异常恢复：启动失败、主机/客户端进程中断、连接断开、中途取消都显示实际状态，恢复使用新会话证据；先恢复电脑设置，再允许重新开始，不能残留错误的“正在游玩”。

性能保持现有原则：硬件路径、有界队列、低延迟输出与音频时钟同步，不通过扩大缓冲或关闭同步满足验收。物理按键到屏幕延迟与平台 API 分段指标分别记录；未实测的边界明确标注。

## 当前基础与缺口

已建立 Rust core、状态模拟器、Ratatui TUI 与真实 Windows/Android TV 后端。Fire TV 已验证硬件音视频串流、能力协商、电脑静音/恢复、客户端与主机中断恢复及 VSYNC 呈现对照；TUI 与未来桌面版共用命令、Snapshot 和 Runtime。

电视启动页、配对后的局域网主机控制、Steam 大屏幕就绪与退出、真实 Fire TV 键鼠导航已经接入同一 core 并完成实机闭环。主机入口为 `host.ps1`，电脑端 `start.ps1 -SteamBigPicture` 保留用于诊断。原生手柄和真实游戏持续游玩尚未通过。GStreamer 主机控制仍复用 Python 实验，媒体热路径是原生 GPU/编码/音频组件；迁移控制语言本身不是此 milestone 的验收结果。

仍需完成：

- 完善多主机发现与选择，当前启动页只保存一个已配对主机。
- 用户登录后主机自动启动与安装流程，当前主机服务在交互式用户会话中运行。
- 游戏运行/正常退出的真实状态探测；大屏幕关闭不代表游戏进程已退出。
- 原生手柄游戏内兼容与断线释放；键鼠导航通过不等于手柄支持。
- 固定游戏持续游玩与完整退出的实机回归，以及会话间同步目标等待和少量长帧的继续定位。

## 接下来先做什么

电视按钮到 core 的控制闭环与 Steam 大屏幕生命周期已经打通，见 [实机记录](tv-host-control-2026-10-12.md)。下一步补原生手柄和游戏生命周期，用固定游戏完成持续游玩与正常退出验收。

后续 milestone 再考虑更多设备/平台、桌面入口和独立媒体能力；Jellyfin 不与当前游戏串流闭环混在一起。
