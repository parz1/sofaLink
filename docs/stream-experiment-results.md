# 1080p60 串流实验实测记录

2026 年 10 月 10 日，Windows 主机上的 GStreamer 与自写 Fire TV 客户端已完成桌面视频串流。TCP 在本次短测试中保持接近 60 fps；UDP 出现少量序列号缺失并造成预测帧丢弃。当前证明了链路可运行，尚未证明游戏输入到电视的总延迟或相对 Sunshine 的优势。

## 条件

- 主机：Windows、NVIDIA RTX 4070 SUPER、GStreamer 1.28.7；D3D11 捕获与 GPU 缩放、NVENC 硬件编码。
- 客户端：Amazon AFTKRT、Fire OS 8.1.8.2、Android 11；自写 Java APK，`OMX.MTK.VIDEO.DECODER.AVC` 硬件解码与 SurfaceView 呈现。
- 视频：1920×1080、目标 60 fps、SDR、H.264 Baseline、20 Mbps、GOP 15、无 B 帧与前瞻、约一帧 VBV。
- 同一局域网，电脑有线连接；没有完整记录盒子端物理网络路径、电视型号或游戏模式，不推断这些因素的影响。
- 客户端请求应用期间的 1080p60 输出模式，退出后已检查 Fire OS 恢复原显示模式。
- 不包含音频、游戏手柄操作、高速摄影或 Sunshine 同条件测试。

## 测量

使用每秒一次的主机、客户端统计。汇总排除启动前三秒及最后一秒；下表延迟是每秒 p50 的中位数，不能当作整段视频所有帧合并的 p50。

| 项目 | TCP 桌面测试 | UDP 桌面测试 |
| --- | --- | --- |
| 记录时长 | 45.11 秒 | 60.75 秒 |
| 纳入汇总的客户端采样 | 41 次 | 55 次 |
| 帧率中位数 | 59.95 fps | 59.91 fps |
| 每秒帧率范围 | 57.95–61.95 | 17.99–61.92 |
| 低于 50 fps 的采样 | 0 | 11 |
| 编码器输入到编码输出 | 6.30 ms | 6.16 ms |
| 客户端首包到解码输出 | 8.11 ms | 8.37 ms |
| 客户端首包到 Surface 呈现 | 65.31 ms | 65.93 ms |
| 每秒呈现 p95 的中位数 | 85.03 ms | 84.58 ms |
| 测量区间 RTP 缺失序列号 | 0 | 65 |
| 损坏帧 | 0 | 16 |
| 队列丢弃或等待 IDR 丢弃的帧 | 0 | 52 |

整数按秒回调计数和调度边界会让单秒统计略高于 60 fps，不表示视频配置变成了 62 fps。TCP 未丢失应用层 RTP 包不代表底层网络绝对没有丢包或重传；本实验没有采集 TCP 重传计数。

UDP 中的缺失序列号包括超过 2 ms 乱序窗口后被视作缺失的包，不能单凭此计数判断是网络、内核缓冲还是接收线程丢包。原始 TCP 日志保存在 `local/benchmark-tcp-1080p60.jsonl`，UDP 日志保存在 `local/benchmark-1080p60.jsonl`，均不纳入 Git。

## 结论和下一步

当前默认使用 RTP over TCP，保留 UDP 对照入口。TCP 在本次约 45 秒的桌面测试中没有记录到损坏帧或队列丢帧；需要更长时间和实际游戏负载验证。UDP 的少量序列号缺失会破坏预测帧参考，当前通过等待下一个 IDR 恢复。

约 65 ms 的客户端呈现时间已经包含约 8 ms 的接收后解码时间，两者不能相加。主机编码时间也不能直接与客户端呈现时间相加得到完整延迟，因为尚未计入捕获、缩放、跨设备传输及 HDMI/电视显示处理。只有呈现回调的数据，也不足以确定等待全部发生在哪个具体显示模块。

下一步重点是记录解码输出到 Surface 呈现的逐帧等待、检查显示队列与帧节奏，再用双屏计时板和高速拍摄测量相对物理显示延迟。协议稳定性、真实游戏画质和长时间帧率应一起比较，避免用单个指标决定串流引擎。
